# Mango Overlay Decky 架构

状态：双模式首发实现完成，等待正式包的桌面模式到游戏模式设备验收
日期：2026-08-06

## 目标

Mango Overlay Decky 是面向 SteamOS 的绘制平台，第一版同时支持游戏模式以及桌面模式中启动的游戏。其他程序拥有各自的提供者画布，可以指定坐标并绘制文字、图片、GIF 等元素，由覆盖层负责合成。

桌面游戏渲染器是游戏进程内的 MangoHud 注入路径，与普通 KDE 桌面常驻窗口不是同一个需求。

项目只负责绘制平台本身，不采集游戏 FPS，也不内置硬件监控业务。

## 第一版范围

包含：

- 在 SteamOS 游戏模式现有的 Gamescope 外部覆盖层中绘制第三方内容。
- 在 KDE 中启动的原生、Steam Runtime 与 Proton 游戏内绘制同一套第三方内容。
- 同时提供 `x86_64` 与 `i686` Vulkan/OpenGL 注入运行时和单一桌面启动接口。
- 保持 Steam 对 MangoApp 的显示开关、预设和布局控制可用。
- 提供同一用户下的本地 IPC，允许多个程序同时发布可定位的绘制内容。
- 提供 Decky 页面管理启用状态、显示策略、提供者状态和诊断信息。
- 扩展版无法启动时自动回退到系统 `/usr/bin/mangoapp`。
- 安装、更新和卸载不修改 SteamOS 的只读系统分区。

暂不包含：

- KDE 桌面上的常驻覆盖窗口。
- FPS 或交换链探针。
- 替第三方程序采集业务数据。
- 替换 Gamescope、Steam 或系统 `/usr/bin/mangoapp`。
- 允许提供者在 MangoApp 进程中执行代码或直接持有 ImGui 状态。

## 系统关系

目标架构通过同一场景接口连接不同渲染适配器：

```text
绘制提供者 ──本地 IPC──> mango-overlayd 场景代理
                                  ├──> 游戏模式渲染器 ──> MangoApp / Gamescope
                                  ├──> 桌面 Vulkan 渲染器
                                  └──> 桌面 OpenGL 渲染器

Decky 插件 ──控制接口─────────────> 场景代理与稳定生命周期助手
```

第一版的运行关系为：

```text
绘制提供者 ──本地 IPC──> mango-overlayd ──已提交场景──> 扩展 MangoApp
                                                            │
Steam ──MangoHud 配置与 preset──────────────────────────────┤
                                                            ▼
                                             Gamescope external overlay

Decky 插件 ──控制接口──> 配置、状态、诊断与安全切换
```

桌面游戏从同一个活动运行时进入：

```text
Steam 启动选项
  -> launcher.py desktop -- %command%
       -> x86_64/i686 OpenGL shim
       -> x86_64/i686 Vulkan implicit layer
       -> SceneClient -> SceneSnapshot -> ImGuiSceneRenderer
       -> mango-overlayd
```

SteamOS 游戏模式的启动链保持不变：

```text
gamescope-session.target
  -> gamescope-mangoapp.service
  -> Mango Overlay 启动保护器
       -> 扩展 MangoApp
       -> 失败时 /usr/bin/mangoapp
```

项目只通过用户级 systemd drop-in 改写 `gamescope-mangoapp.service` 的 `ExecStart`。系统原文件和系统 MangoApp 保持原样。

## 组件边界

### 扩展 MangoApp

- 以 SteamOS 当前 MangoHud/MangoApp 版本为兼容基线。
- 保留 Gamescope 消息协议、Steam preset 和原有性能层行为。
- 在原有绘制阶段合并各提供者画布的场景快照。
- 不在渲染线程解析无界输入，不等待 IPC，也不执行提供者代码。

当前主机基线：

- Gamescope：`3.16.23.5-1`
- MangoHud：`0.8.3.rc1.r24.g33c2c7dd-3`
- MangoHud 提交：`33c2c7ddbb72c15e19a42163d75424d5804f8ec8`

在完成协议兼容测试前，不直接跟随 MangoHud 最新 `master`。

### 桌面游戏渲染器

- 普通桌面游戏使用 MangoHud 的游戏内注入路径，不使用 MangoApp 或 KDE layer-shell。
- Vulkan 游戏通过 MangoHud 隐式层在交换链提交前绘制；OpenGL 游戏通过 MangoHud shim 在交换缓冲前绘制。
- OpenGL 启动入口始终是 `libMangoHud_shim.so`；shim 再按
  `MANGOHUD_OPENGL_LIBS` 加载同架构的 `libMangoHud_opengl.so`。直接预加载后者
  对 Wine/Proton 不足，因为 Wine 可能通过 `dlopen/dlsym` 绕过普通符号拦截。
- Proton 的 D3D11/DXVK 与 D3D12/VKD3D 路径不维护第二套覆盖层；只要最终调用宿主 Vulkan，
  就复用同一个 Vulkan 隐式层和场景渲染器。兼容层差异只存在于启动传播、ABI 和
  Runtime 文件可见性适配。
- 需要同时提供 `x86_64` 和 `i686` 运行时，以覆盖原生游戏和 Proton 进程。
- 每个游戏进程都是共享场景接口的只读渲染实例；场景语义和资源 ID 与游戏模式一致。
- Vulkan、OpenGL 和 MangoApp 各自维护 GPU 纹理，不能把后端私有纹理句柄放进公共接口。
- 对外只暴露 `launcher.py desktop -- %command%`。启动器从内容寻址的活动运行时选择
  `$LIB` 对应 ABI，清理冲突的 MangoHud shim，再统一设置 manifest、preload、私有库
  搜索路径和场景 socket；调用方不区分原生、Steam Runtime 或 Proton。

### 版本兼容边界

- 游戏模式以仓库固定的 MangoHud/MangoApp 提交和 SteamOS Gamescope 协议为兼容
  基线；启动自检失败时回退系统 `mangoapp`，不承诺任意 MangoHud master 或
  Gamescope 版本都能直接替换运行时。
- 桌面渲染器的提供者协议是独立的版本化合同；渲染器通过能力协商拒绝未知必需
  能力，因此 daemon、游戏模式和桌面渲染器可以按合同演进。
- 图形注入兼容性由架构和宿主入口决定：原生 GLX/EGL/Vulkan、SteamRT4、Proton
  各有可重复的验收矩阵；每种 ABI 使用独立 ELF 产物，不把 32 位库注入 64 位进程。
- Steam Runtime、Proton、MangoHud 或 Vulkan loader 升级后必须重新构建并运行对应
  矩阵。通过矩阵表示“已验证兼容”，不是对未来版本的无限承诺。

### 场景代理 `mango-overlayd`

- 作为独立用户进程持有场景状态，通过用户级 systemd socket 按需启动。
- 通过本地 IPC 分别提供写入场景、读取已提交场景和管理策略的角色接口。
- 连接建立时协商协议版本和能力，未知必需能力必须明确拒绝。
- 维护提供者画布、绘制元素和资源。
- 保存保留式场景；提供者只发送元素的创建、更新和删除，不逐帧重发整幅画面。
- 每批修改只有在 `commit` 后原子可见，渲染器不会看到半完成场景。
- 渲染器首次连接时获得完整快照，之后只接收已提交事务形成的有序变化。
- 为游戏模式渲染器和未来多个桌面游戏渲染器提供相同语义。
- 提供者连接断开后移除其画布，不能留下永久脏状态。首版没有独立心跳协议。
- 后端差异不得泄漏为两套提供者协议。
- IPC、资源验证或图片解码错误不能直接终止渲染器。

首版 IPC 使用 `$XDG_RUNTIME_DIR/mango-overlay-decky.sock` 上的 Unix `SOCK_SEQPACKET`、固定消息头和 FlatBuffers 载荷。大资源通过 `SCM_RIGHTS` 传递只读文件描述符。

### 提供者接口

- 版本化 wire protocol 是兼容性合同，内部 C++ 类型和 ImGui 状态不属于接口。
- 首版提供稳定 C ABI、轻量 C++ 封装、Python 封装和 Rust 封装。
- 其他语言可以通过 C ABI 或直接实现 wire protocol 接入。
- TypeScript 等其他专用 SDK 在出现真实调用方后再增加。

### 提供者身份与授权

- 提供者注册稳定 `application_id`，每次连接另有临时 `instance_id`。
- 多个相同应用实例可以同时拥有独立画布，用户设置按 `application_id` 保存。
- 所有连接通过 Unix 凭据验证为当前登录用户。
- “要求新提供者审批”是可选总开关，默认关闭。
- 开关关闭时，新提供者可立即显示；开启后，未知应用进入等待授权状态。
- 用户可以随时撤销应用权限、隐藏画布或调整提供者层级。
- 同一 UID 的进程不构成安全隔离，`application_id` 也是提供者自声明值；审批功能用于防止误显示和便于管理，不承诺抵御当前用户下的恶意程序。

### 启动保护器

- 启动前读取受所有权和权限约束的安装状态，并验证活动扩展二进制。
- 扩展文件无效、无法启动或运行中意外退出时，在同一 systemd 服务内立即执行系统 MangoApp，不形成扩展重启循环。
- systemd 正常停止会话时只转发信号并退出，不写安装状态，也不触发回退。
- 回退系统 MangoApp 时移除项目私有库路径，避免系统二进制加载包内依赖。
- 不依赖 Decky 前端正在打开。
- 同一稳定启动模块还承担桌面游戏入口，但桌面游戏退出只结束该运行会话，不触发
  MangoApp 回退，也不改变安装、更新或卸载状态。

### Decky 插件

- 展示运行版本、后端选择、连接的提供者和最近错误。
- 安装或移除用户级 service drop-in。
- 提供测试绘制和安全重启操作。
- `_unload` 只释放插件后端进程资源，不改变安装状态，也不停止扩展覆盖层。
- `_uninstall` 只记录待确认卸载并启动延迟核对，不能直接删除运行时或 service drop-in。
- 新版本插件启动时取消待确认卸载，并执行原子更新事务。
- 只有确认 Decky 插件目录确实不存在时，稳定生命周期助手才执行最终卸载。
- Decky 的“禁用插件”只停止管理界面和后端；扩展覆盖层由项目自身总开关控制。
- 更新成功后自动切换运行时，不提供独立的“更新后台”步骤。
- 同一个 Decky 包携带游戏模式运行时、桌面双 ABI 注入库和 Vulkan manifest；两种
  模式随同一内容寻址修订一起验证、激活和回滚。

Decky Loader 当前更新流程也会调用 `_uninstall`，所以插件回调名称不能作为用户意图。详细状态机见 [lifecycle.md](./lifecycle.md)。

### 稳定生命周期助手

- 安装在插件目录之外的用户可写位置，在 Decky 替换或删除插件目录时仍可运行。
- 持有生命周期锁、记录对外版本、内容寻址的活动/回滚运行时修订以及待确认卸载记录。
- 为安装、更新、最终卸载和崩溃回退提供同一个幂等事务入口。
- 休眠、关机、图形会话结束或普通进程退出不得创建卸载记录。
- 新版本验证失败时继续使用 `previous`，不得因为更新失败破坏当前可用覆盖层。

## 提供者画布

### 场景模型

- 每个提供者拥有独立的保留式场景。
- 元素有稳定 ID；提供者按 ID 创建、更新或删除元素。
- 多元素变化通过场景事务一次提交；提交失败时旧场景保持不变。
- 提供者停止更新时，平台继续绘制最后一个完整快照。
- 连接断开后，平台移除该提供者的整个画布。
- 场景支持 `Group`，子元素继承父级位移、旋转、缩放、透明度和裁剪。
- 分组深度和每个分组的子元素数量均有硬上限。

### 坐标模型

- 默认参考画布为 `1280×800`，提供者可以声明其他宽高；参考宽高决定逻辑尺寸密度，不冒充输出分辨率。
- 渲染器从当前输出自动生成逻辑视口并等比缩放，避免图像和文字被拉伸；输出宽高比多出的方向扩展为可用空间。
- 有可见提供者时，MangoApp 承载窗口必须覆盖 Gamescope 报告的完整当前输出，不能沿用进程启动时的初始窗口尺寸。
- 根元素的九个锚点相对当前输出视口定位，因此输出切换不依赖用户维护分辨率设置。
- 提供者可以使用任意位置，包括覆盖整个画面；平台负责裁剪到有效输出区域。
- 提供者文字使用独立的高密度字体栅格，避免输出缩放时放大系统统计所用的低分辨率字形。

### 合成模型

- 提供者可以控制自己画布内元素的 `z-index`。
- 提供者之间的前后顺序和可见性由用户控制。
- 提供者不能自行越过全局层级，强制覆盖其他提供者。
- 第一版不向提供者转发触摸、鼠标或手柄输入。

### 第一版绘制元素

- 文字。
- 直线和折线。
- 矩形、圆角矩形和圆。
- PNG、JPEG 和 WebP 静态图片。
- GIF 动画。
- 透明度、旋转、缩放和矩形裁剪。
- 分组与继承变换。

文字使用 MangoApp 当前字体并支持 UTF-8 文本、字号和颜色。第一版不提供单独的字重、对齐、自动换行或自定义字体接口，也不支持视频、SVG、自定义着色器或在覆盖层进程中执行提供者代码。

### 资源与负载限制

- 允许全屏画布，但每个提供者都有元素数、纹理内存和消息大小上限。
- 达到上限只拒绝该提供者的新操作，不影响其他提供者或系统覆盖层。
- 绘制资源上传一次并通过资源 ID 引用；平台不读取提供者指定的任意文件路径。
- 小资源可直接随协议传输，大资源使用只读内存文件描述符传递。
- GIF 在非渲染线程解码和缓存；提供者控制播放、暂停、速度和暂停帧，动画默认循环。
- IPC 和解码不进入渲染线程；GPU 上传限制为每个绘制帧最多一帧纹理。
- 单资源编码数据上限为 8 MiB、解码数据上限为 32 MiB；每提供者和全局还有独立累计预算。
- 每个渲染后端独立维护 GPU 资源缓存；公共协议中只出现资源 ID，不出现 `ImTextureID`、Vulkan 或 OpenGL 对象。

## 数据路径约束

- 渲染线程只读取已完成的场景快照。
- IPC 接收、资源解码、校验和场景合并在非渲染线程完成。
- 对连接数、提供者数量、元素数量、资源大小和字符串长度设置上限。
- `SOCK_SEQPACKET` 保持消息边界，每个连接串行处理请求，不建立无界应用队列。
- 提供者崩溃、发送损坏消息或中途断开都不能把半场景发布给渲染器。

## 信任边界

- 拒绝其他 UID 连接，所有消息仍按不可信输入校验。
- 主要防护目标是错误、失控资源和无意冲突，确保一个提供者不能拖垮其他画布或系统覆盖层。
- 不把同一登录用户下的进程视为强安全边界；该用户本来可以读取配置、终止进程或调试其他同 UID 进程。
- 场景代理不使用网络端口，不读取提供者指定路径，也不以 root 身份解析图像或场景消息。

## 显示策略

提供者可以请求：

- `game_only`：只在游戏获得焦点时显示第三方内容。
- `steam_only`：只在 Steam 界面获得焦点时显示。
- `always`：当前 SteamOS 图形会话中始终显示。

未声明策略时默认为 `game_only`。用户设置拥有最终决定权，可以隐藏单个提供者或关闭全部第三方内容。

Steam 原生性能统计与第三方画布分别控制：Steam 性能层设为关闭时，第三方画布仍可按项目总开关和提供者显示策略继续显示。Steam 会话尚未完成初始化时保持隐藏，避免覆盖 OOBE 和启动界面。

系统统计内容默认绘制在所有提供者画布上方。用户可在高级设置中调整其全局层级；绘制提供者不能自行越级。

## 仓库边界

这是一个 SteamOS 专用单仓库，包含：

```text
broker/      mango-overlayd 与控制器
client/      稳定 C ABI、C++、Python 与 Rust 封装
renderer/    共享绘制逻辑和各渲染适配器
plugin/      Decky 前端和 Python 后端
packaging/   Steam Runtime 4 构建、Decky 打包与 SDK 验收
protocol/    版本化消息协议
resource/    图片与 GIF 解码
scene/       保留式场景和策略
tools/       示例提供者与嵌套 Gamescope 工具
docs/        架构、协议、生命周期、调试和 ADR
```

仓库以 SteamOS 当前 MangoHud 提交为 Git 历史基线，在隔离目录和独立提交中加入本项目模块。不得复制一份失去历史的 MangoHud 源码；后续同步上游时必须保留清晰、可审计的项目差异和原许可证。

## 尚待验证

1. 同一个正式 Decky 包从 KDE 桌面游戏回归到真实游戏模式的完整顺序验收。
2. 当前无外接屏硬件，真实输出切换保留为延期人工验收项。
3. 固定功耗真实游戏中的空载和典型场景发布性能预算。
